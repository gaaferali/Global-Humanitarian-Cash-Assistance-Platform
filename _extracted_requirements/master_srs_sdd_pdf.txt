1. Executive Summary 
H-CAP is a secure, multi-tenant web platform for managing humanitarian cash-assistance 
operations from program setup through household intake, beneficiary review, eligibility and 
enrollment decisions, simulated payment execution, complaints, post-distribution monitoring, 
budgeting, reporting, and audit. 
 
The MVP is deliberately constrained. React with TypeScript provides the staff-facing 
frontend. Django and Django REST Framework provide authentication, tenant scoping, 
authorization, validation, domain services, REST APIs, payment simulation, AI/automation 
orchestration, and audit generation. PostgreSQL is the authoritative system of record. There 
is no external payment domain server and the system does not move real money. 
 
AI and automation are advisory and operational-support layers. Deterministic Django 
validation runs first. Advisory AI may identify data-quality issues, possible duplicates, 
anomalies, eligibility evidence, PDM themes, and report drafts. Automation may issue 
reminders, route queues, calculate dashboards, execute bounded simulated retries, and 
prepare work for staff. AI must not silently deny eligibility, accuse a person of fraud, approve 
a high-impact decision, or mark a simulated payment successful without an authoritative 
Django workflow and a recorded event. 
 
The MVP uses exactly 12 persisted tables. To preserve that boundary, the eligibility result 
remains part of enrollment, budget line items are stored as JSONB within budget, and PDM 
responses are collected or summarized through application/API payloads rather than a 
dedicated PDM table. Dedicated PDM persistence, dedicated AI-signal persistence, and 
reconciliation-item persistence are Phase 2 extensions.

3. Product Scope and Objectives 
3.1 MVP objectives 
The MVP must demonstrate one coherent vertical workflow rather than a collection of 
disconnected screens. Staff must be able to create a program, register a household and 
beneficiaries, record consent and verification, review eligibility, approve enrollment, create a 
simulated payment instruction, execute and inspect simulated payment events, handle 
complaints, inspect budget status, review PDM summaries, and inspect audit history. 
 
The platform must be tenant-aware from the beginning. Every operational query must be 
restricted to the authenticated user’s tenant unless a future, explicitly authorized cross-tenant 
reporting policy is introduced. 
 
The frontend must be suitable for field and operations staff. It should be responsive, low-
bandwidth conscious, keyboard accessible, and prepared for English and Arabic labels and 
right-to-left layout. 
 
3.2 Out of scope for the MVP 
The MVP does not include real payment processing, custody of funds, bank or mobile-money 
credentials, external payment APIs, a separate payment domain server, a configurable 
workflow-rule database, offline synchronization, exchange-rate management, a dedicated 
reconciliation table, multi-step approval chains, or a dedicated AI-signal table.

5. System Architecture 
5.1 Logical architecture 
The system consists of four logical areas, with the last three implemented within the 
application boundary: 
 
1 Staff and React presentation. Authorized staff use dashboards, forms, queues, 
timelines, and AI/automation pages. 
2 Django REST and domain services. Django authenticates requests, resolves tenant 
and role, validates payloads, executes state transitions, runs the simulated payment 
service, calls AI/automation services, and writes audit records. 
3 AI and automation services. These services produce advisory outputs and 
deterministic operational actions. They do not own authoritative beneficiary, 
eligibility, enrollment, or payment outcomes. 
4 PostgreSQL system of record. PostgreSQL stores the 12-table MVP model and 
append-only payment and audit history.

5.2 Architectural rules 
The frontend may perform client-side validation for immediate feedback, but Django must 
repeat validation and is the authoritative validation layer. The frontend must never submit an 
arbitrary status transition for direct persistence. High-impact changes must call a domain 
service that validates the current state, actor role, tenant scope, required relationships, and 
idempotency conditions. 
 
The payment simulator is an internal Django service. It creates a payment instruction and 
appends simulated payment events such as CREATED, SUBMITTED, SUCCESS, FAILED, 
and REVERSED. It never calls a bank, mobile-money provider, cash agent, voucher system, 
or external payment domain server. 
 
The database must protect tenant scope through foreign keys, application-level query 
scoping, object-level permission checks, and indexes. Audit events and payment events are 
append-only at the application and database-permission levels.

6. Frontend Design Baseline 
The React frontend is organized around operational workflows, not merely around database 
tables. The redesign target is a neutral public-sector/humanitarian interface that does not 
imitate protected agency branding. 
 
6.1 Visual language

links, white cards for operational content, and a neutral gray page background. Use green for 
verified or successful states, amber for pending review or attention required, red for failure or 
safeguarding-critical issues, and gray for inactive or closed states. Every status must include 
text; color must never be the only signal.

a main content area with summary cards, filters, tables, timelines, and one clear primary

9.1 Required relationships 
tenant has many user, program, household, and audit_event records. program has many 
household, enrollment, and payment_channel_config records and one MVP budget. 


--- PAGE 11 ---
household has many beneficiary records. beneficiary has many enrollment and complaint 
records. enrollment authorizes many payment_instruction records, although normal 
operations should enforce one active instruction per cycle. payment_instruction has many 
payment_event records and may be referenced by complaints. user is recorded as creator, 
approver, assignee, recorder, or audit actor where applicable. 
 
9.2 Key constraints 
All primary identifiers are UUIDs. Monetary values use NUMERIC(18,2) and must be 
positive where applicable. Currency uses a three-character code. The program transfer 
amount must be greater than zero. The enrollment relationship is unique for (program_id, 
beneficiary_id). The payment idempotency key is unique. Tenant ownership must be verified 
before every read and write. Audit and payment event records are append-only. 
 
9.3 Budget line representation 
The budget table contains a JSONB line_items field. Each item should contain a stable client-
generated key, category, planned amount, actual amount, and optional notes. The API 
validates that values are numeric, non-negative, and sum consistently with the budget policy. 
A dedicated budget_line table is a Phase 2 normalization option. 
 
9.4 PDM representation 
The MVP exposes PDM submission and summary endpoints, but does not add a 
pdm_response table. During the demonstration, the service may retain redacted payloads in 
controlled application storage or audit payloads and compute summaries from the submitted 
request. If durable, queryable PDM history is required for production, add pdm_response in 
Phase 2. 
 
 
 
10. Payment Simulation Design 
Payment is a demonstration workflow and not a financial integration. The simulated payment 
service lives inside Django. 
 
10.1 Allowed flow 
DRAFT → CREATED → SUBMITTED → SUCCESS or FAILED; a successful or failed 
instruction may later be marked REVERSED only through an explicitly authorized 
simulation action. Every transition is validated by Django and appends a payment_event. 
 


--- PAGE 12 ---
10.2 Simulation controls 
The finance page may offer controlled actions such as Simulate success, Simulate failure, 
Retry, and Simulate reversal. Each action must show that it is a simulation. The interface 
must never display provider settlement language, bank confirmation, or a claim that money 
was received. 
 
10.3 Safety rules 
The service must not make outbound provider calls. A payment cannot be created unless the 
enrollment is approved and the channel configuration is active. A repeated request with the 
same idempotency key returns the existing instruction. A simulated success requires a 
generated authoritative event and an audit event.

11.3 AI governance requirements 
Each advisory output should carry a model or rule version, input scope, generation time, 
confidence where available, and a human-review indicator. The service must redact 
unnecessary personal data before sending context to a model. If an AI service is unavailable, 
the system must return a useful non-AI fallback such as deterministic validation results, a 
manual-review queue, or a report template. 
 
The assistant must not expose raw national identifiers, full phone numbers, passwords, 
unrestricted audit payloads, or another tenant’s data. The UI must label AI-generated content 
as advisory.

14. Non-Functional Requirements 
14.1 Security and privacy 
Use Django’s secure password hashing and secure session/token handling. Use HTTPS in 
deployment. Enforce tenant-scoped querysets and object-level permissions. Do not expose 
password hashes, raw national IDs, full phone numbers, or unrestricted audit payloads to 
React. Redact sensitive values in audit JSONB. Store secrets outside source control. 
 
14.2 Reliability and integrity 
Use database transactions around high-impact state changes. Enforce unique idempotency 
keys. Make simulated payment retries bounded and repeat-safe. Preserve failed and reversed 
events rather than overwriting them. Return visible failure states. Ensure audit generation is 
part of the same transaction where the operation’s integrity requires it. 
 
14.3 Usability and accessibility 
Support keyboard navigation, visible focus, readable contrast, responsive tables, clear labels, 
short forms, and status text in addition to color. Externalize English and Arabic labels from 
the start and prepare the layout for RTL. 
 


--- PAGE 22 ---
14.4 Performance and low bandwidth 
Use pagination, filtered queries, compact payloads, lazy loading for dashboards, and server-
side aggregation for summary cards. Avoid sending unnecessary beneficiary details to the 
browser. 
 
14.5 Maintainability 
Use modular Django apps, typed TypeScript API contracts, migrations, automated tests, 
service-layer ownership of state transitions, and documented AI/automation interfaces. Keep 
AI prompts, rule versions, and fallback behavior versioned in application code.

Unit tests cover Django models, validators, permissions, domain services, AI scoring 
functions, and status transitions. Integration tests cover REST endpoints with PostgreSQL 
transactions. End-to-end tests cover the staff workflow from program creation through 
simulated payment and audit review. Security tests cover authentication, tenant isolation, 
object-level access, injection resistance, and sensitive-data masking. AI tests cover advisory 
behavior, confidence/source fields, human review, overrides, and non-AI fallback.

16. Reports and Operational Views 
The MVP should provide deterministic reports for program summary, beneficiary 
registration, eligibility/enrollment review, simulated payment instructions, simulated payment 
event history, derived reconciliation support, PDM summary, complaint status, budget status, 
audit history, and AI/anomaly review. AI can draft narrative text, but the underlying metrics 
must come from authorized Django queries and the draft must remain visibly provisional 
until approved by a human. 
 
Derived reconciliation support compares payment instruction amount, currency, simulated 
event status, provider-reference placeholder, and idempotency information. It is a 
view/service in the MVP, not a separate persisted reconciliation table. 
 
 
 
17. Delivery and Deployment Baseline 
The MVP may be deployed as one Django application process behind a standard HTTPS-
capable web server, with PostgreSQL as the database. React may be built and served as static 
assets or hosted through the selected frontend delivery mechanism. The logical application 
boundary remains Django REST plus PostgreSQL plus AI/automation services. No separate 
payment domain server is needed. 
 
Scheduled reminders, signal refreshes, or report jobs may initially run through Django 
management commands or controlled administrative actions. A task runner and message 
broker can be introduced later only if the operational workload requires it.
